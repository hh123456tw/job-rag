# 免費雲端 CPU 可行性量測（票 18 預備）

目標條件：Hugging Face Spaces 免費層，2 vCPU、16 GB RAM，閒置會休眠。
本檔所有數字來自本機模擬，**不是雲端實測**。沒有上傳任何東西，沒有連線任何雲端服務。

## 結論

**可試。** 門檻是「預熱後單次查詢中位數 > 3 秒，或冷啟動 > 3 分鐘 就不建議」。本機模擬兩者都遠低於門檻（見下表）。

但這只是粗估，三個沒量到的風險：

1. **模型下載時間沒量。** bge-m3 的權重檔 2.27 GB。Spaces 的磁碟是暫存的，每次重啟（含休眠後喚醒）都可能要重新取得。本機是從本機硬碟讀。這一項可能是雲端冷啟動的最大部分，要上線後才知道。
2. **雲端核心速度沒量。** 本機是 Intel 12 代 CPU。我把行程綁在 2 個邏輯核心上，並用兩種核心各跑一次（見下），慢的那組約比快的慢 2 倍。雲端 vCPU 可能比慢的那組更慢。就算再慢 5 倍，估計中位數仍約 1.4 秒，仍在門檻內，但這是推算，不是量到的。
3. **休眠喚醒 = 完整冷啟動。** 面試官第一次點開時要等整段冷啟動。現場演示前要先自己打開預熱。

## 量測方法

腳本：`eval/measure_spaces.py`（`python -X utf8 eval/measure_spaces.py`）。

- 每一項都在新的行程裡跑。環境變數 `OMP_NUM_THREADS=2`、`MKL_NUM_THREADS=2`，程式內 `torch.set_num_threads(2)`（量到的執行緒數為 2）。
- 行程用 Windows 的 affinity 綁在 2 個邏輯核心。跑兩次：核心 0、1（遮罩 `0x3`，同一個效能核心的兩個執行緒）與核心 16、17（遮罩 `0x30000`，節能核心，較慢）。
- 資料來源是公開版語料包 `dist/public_bundle/`（`JOB_RAG_BUNDLE`），不設 `JOB_RAG_CORPUS`，也不用 `.cache`（冷啟動用空的快取資料夾）。所以量到的是「上線時真的會跑的路徑」：只編碼查詢句，不編碼段落。
- 模型：本機 `models/bge-m3`（`JOB_RAG_MODELS`），沒有下載任何東西。
- (1) 載入：從 `import torch` 到模型載入完成，再編碼一次短句。記憶體是行程的工作集峰值。
- (2) 查詢：先 `search("預熱")` 一次，再依序用評估題的前 20 題各查一次，`gate=False`，k=3。分別量預設方式 bge-m3 與 hybrid（BM25＋bge-m3）。
- (3) 冷啟動：啟動 `python app.py`（含 Flask 與啟動預熱執行緒），到第一次對 `/?q=…` 取得有原文結果的頁面為止。再量一次網頁查詢的往返時間。

## 數字

| 項目 | 核心 0、1（較快） | 核心 16、17（較慢） |
|---|---|---|
| import torch 與 retrieval | 2.4 秒 | 4.6 秒 |
| 載入 bge-m3 | 9.3 秒 | 18.6 秒 |
| 載入後第一次編碼 | 0.33 秒 | 0.53 秒 |
| 載入行程的記憶體峰值 | 2.04 GB | 2.04 GB |
| 預熱（讀語料包、載入、建索引、編碼） | 9.8 秒 | 20.3 秒 |
| 預熱後單次查詢，bge-m3，中位數（20 次） | 0.14 秒 | 0.28 秒 |
| 預熱後單次查詢，bge-m3，最慢 | 0.20 秒 | 0.57 秒 |
| 預熱後單次查詢，hybrid，中位數（20 次） | 0.15 秒 | 0.34 秒 |
| 預熱後單次查詢，hybrid，最慢 | 0.98 秒 | 1.92 秒 |
| 查詢行程的記憶體峰值 | 2.12 GB | 2.12 GB |
| 冷啟動：行程啟動到第一次可查詢 | 13.8 秒 | 28.0 秒 |
| 啟動後網頁查詢往返 | 0.17 秒 | 0.31 秒 |
| 伺服器行程記憶體峰值 | 2.07 GB | 2.07 GB |

說明：

- hybrid 的最慢值是第一次 hybrid 查詢（要建 BM25 索引、載入 jieba 詞典），不是常態；其餘 19 次接近中位數。
- 記憶體約 2 GB，遠低於 16 GB。
- 冷啟動不含：取得模型的時間、取得 Python 套件的時間、容器啟動時間。

## 限制

- 本機 CPU 與雲端不同，且 Windows 的 affinity 只限制排程，不限制快取與記憶體頻寬；結果只能當粗估。
- 作業系統檔案快取是熱的（模型檔最近才讀過），所以載入時間偏樂觀。
- 20 次查詢用的是評估題原句，句子長度偏短；很長的問句會稍慢。
- 只量單一使用者、一次一個請求。多人同時查詢沒量。
- 「查無」門檻與評分不受此量測影響。用語料包評分的結果與原始語料相同（見票 18a 的提交說明）。

## 語料包的限制（上線前要知道）

- 語料包只含 bge-m3 的向量。`bm25`、`bge-m3`、`hybrid` 可用；`bge-small-zh`、`e5-large` 在語料包模式會報錯（明確訊息）。App 預設用 bge-m3，不受影響。
- 查詢句仍要用 bge-m3 模型編碼，所以雲端一定要有 bge-m3 模型。

## 若要上線：需要的檔案與設定

只列清單，這次沒有建立或上傳任何一項。

檔案（上傳到 Space 的內容，都只含公開內容）：

- `app.py`、`job_rag/`、`eval/questions.json`
- `/about` 頁讀的評估輸出：`eval/results_methods.json`、`eval/results_generation.json`（上傳前再看一次內容，確認只有公開內容）
- `dist/public_bundle/segments.jsonl`、`dist/public_bundle/vectors.npz`（約 1.9 MB）
- 相依套件清單：目前 `requirements.txt` 只有 flask、jieba、rank-bm25、pytest。雲端還需要 `torch`（CPU 版）、`sentence-transformers`、`faiss-cpu`、`numpy`。要另寫一份雲端用的清單。
- 啟動設定（Spaces 的 Docker 或 app 檔），並用單一 worker 啟動（避免模型載入多份）。
- bge-m3 模型：由 Hugging Face 取得，放到 `JOB_RAG_MODELS` 底下的 `bge-m3/` 資料夾。要在建置階段下載，不要放在 git 裡。

**不得上傳**：原始調查檔、`.env`、`.cache/`、`models/`（若模型改在建置階段下載）。

環境變數（只寫名稱；值由主機的機密設定提供，不寫進程式或 repo）：

- `JOB_RAG_BUNDLE`：語料包資料夾（不是機密）
- `JOB_RAG_MODELS`：模型資料夾（不是機密）
- `JOB_RAG_PORT`：服務連接埠（Spaces 預設 7860）
- `OMP_NUM_THREADS=2`
- `DEEPSEEK_API_KEY`：機密。只有「整理成答案」要用；沒設時該按鈕會明確回報錯誤，原文結果不受影響。
- 選用：`DEEPSEEK_MODEL`、`JOB_RAG_DETECT`、`JOB_RAG_DEDUPE`

使用者要自己做的事：建立 Hugging Face 帳號與 Space、在 Space 設定裡填入機密、決定 Space 公開或私人。
