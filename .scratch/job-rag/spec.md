# 求職情報問答：規格

狀態：待 tracker 設定後發佈（`ready-for-agent`）。名詞見 [GLOSSARY.md](GLOSSARY.md)。
決策來源：2026-11-16 的討論（Q1–Q18 全部接受）。

## Problem Statement

11/19 廠商媒合活動有 16 家公司，其中 11 家下午在現場面談。我已經做完每家的深查檔和 104 職缺檔，共約 230 KB。現場每跟一個人談，我要在幾十份檔案中找：這家做什麼、有什麼職缺、可以問什麼、我的專案哪個對得上。翻檔太慢，也無法跨公司問「哪幾家要用 FastAPI」。

另外，我的履歷技能欄寫了 RAG（FAISS、BGE-M3），但三個專案都沒有我自己寫的 RAG。面試官會追問，我答不出來。我需要一個自己做、自己能解釋、有評估數字的小型 RAG 專案。

## Solution

做一個在筆電上跑的問答工具，語料是我的求職調查檔。

- 輸入問題或點按鈕，不到 1 秒顯示最相關的 3 個段落（原文結果），標出公司、檔名、標題。
- 按「整理成答案」才呼叫 DeepSeek，產生附出處的白話答案。
- 頂端有 11 顆現場公司按鈕，點了就只搜那一家。下方有 6 顆常用問題和 2 顆查無示範。
- 兩種模式：演示模式（預設，只含公開事實段落，可給面試官看）和查詢模式（含私人段落，橘色標示）。
- 第二分頁「研究結果頁」，一頁呈現 5 種檢索方式在 30 題上的成績。這頁同時是履歷與面試時可以講的內容。

## User Stories

1. As a 求職者, I want 輸入一個問題就立刻看到最相關的 3 個原文段落, so that 我在現場幾秒內就能得到答案。
2. As a 求職者, I want 每個結果標出公司、檔名和標題, so that 我知道資料出自哪裡、可信度如何。
3. As a 求職者, I want 點一顆公司按鈕後只搜那一家, so that 我跟某位面試官談話時不會看到別家的內容。
4. As a 求職者, I want 11 顆按鈕對應 11 家現場公司, so that 我不必找哪家有來。
5. As a 求職者, I want 6 顆常用問題按鈕（做什麼、職缺、面試問什麼、風險、可問什麼、我的專案對哪個）, so that 我不用在現場打字。
6. As a 求職者, I want 不選公司時能跨 16 家提問（例如「哪幾家要用 FastAPI」）, so that 我能比較公司，這是速查頁做不到的。
7. As a 求職者, I want 按「整理成答案」才呼叫 LLM, so that 預設回應最快，也不耗 API 額度。
8. As a 求職者, I want 整理後的答案附出處段落, so that 我能核對 LLM 有沒有講錯。
9. As a 求職者, I want 系統在語料沒有答案時回答「查無」, so that 它不會亂編，我也不會在現場說錯話。
10. As a 求職者, I want 2 顆查無示範按鈕, so that 我能向面試官展示系統不會亂編。
11. As a 求職者, I want 預設進入演示模式, so that 螢幕被面試官看到時不會露出私人內容。
12. As a 求職者, I want 手動切到查詢模式才看到私人段落, so that 我自己要查「你的對應」「作戰卡」「風險」時才看得到。
13. As a 求職者, I want 查詢模式有明顯的橘色標示, so that 我知道此刻螢幕上有私人資料，不要轉給別人看。
14. As a 求職者, I want 私人段落永遠不送給 DeepSeek, so that 我的求職策略不會傳到第三方伺服器。
15. As a 求職者, I want 查詢模式下私人段落只顯示原文、不能整理成答案, so that 這條規則在畫面上就看得出來。
16. As a 求職者, I want 分類不確定的段落一律當私人段落, so that 錯誤的方向是「多藏」而不是「多露」。
17. As a 求職者, I want API 失敗或沒網路時看到明確錯誤，原文結果照常顯示, so that 現場網路差時仍能查詢，也不會看到假答案。
18. As a 求職者, I want 檢索全在本機執行, so that 查詢文字不會離開我的電腦（除了按整理成答案的公開段落）。
19. As a 求職者, I want 研究結果頁一頁就看完整個評估, so that 面試官問「你怎麼知道這個比較好」時我能直接給他看。
20. As a 求職者, I want 研究結果頁顯示語料規模（幾份檔、幾個段落）, so that 數字有脈絡。
21. As a 求職者, I want 研究結果頁顯示 30 題的組成（25 可回答、5 不可回答）, so that 我誠實說明樣本很小。
22. As a 求職者, I want 5 種檢索方式並列在同一張表, so that 我能說明為什麼選了某一種。
23. As a 求職者, I want 表上有 Hit@1、Hit@3、MRR, so that 我有業界通用的指標可講。
24. As a 求職者, I want 不可回答題的正確拒答率另列, so that 它不污染 MRR。
25. As a 求職者, I want 頁面寫明限制（題少、只能當方向、題目由 AI 草擬並經我核對）, so that 我不誇大結果。
26. As a 求職者, I want 研究結果頁的數字由評估程式輸出、不手寫, so that 頁面和實際執行不會不一致。
27. As a 求職者, I want 同一份結果也輸出成純文字檔, so that 我能直接抄進履歷和 README。
28. As a 求職者, I want 每個預設按鈕的問題取自評估題, so that 我按下去的結果就是我量過的結果。
29. As a 求職者, I want 每個答案旁有「看這題在評估裡的成績」連結, so that 我能展示這題的檢索排名。
30. As a 求職者, I want 評估題由 AI 草擬、我對照原檔逐題確認, so that 金標段落是我認可的，不是 AI 自說自話。
31. As a 求職者, I want 評估題標明金標段落的位置, so that 評分可以自動算。
32. As a 求職者, I want 下載任何模型前先知道實際大小, so that 我決定要不要下載。
33. As a 求職者, I want DeepSeek 金鑰放在不進 git 的設定檔、由我自己填, so that 金鑰不會出現在對話或 repo。
34. As a 求職者, I want 全部語料不進 git, so that 公開 repo 不會洩漏私人段落和廠商評估。
35. As a 面試官, I want 在公開 repo 用 3 家範例語料就能重現流程, so that 我能驗證這個專案是真的。
36. As a 面試官, I want 看到評估方法和限制寫得誠實, so that 我判斷候選人懂得評估而非只會串 API。
37. As a 求職者, I want 一份 60 秒演示腳本, so that 現場演示不會卡住。
38. As a 求職者, I want 一段螢幕錄影備案, so that 現場網路失敗時我仍有東西可播。
39. As a 求職者, I want 履歷只在專案完成後才寫這個專案和 RAG 技能, so that 我只宣稱自己真的做過的事。
40. As a 求職者, I want 專案在履歷上標為「2026/11 個人專案」, so that 不會被誤認為更早的經驗。
41. As a 求職者, I want 組內 RAG（由組員寫的）不寫成我的, so that 面試時被追問不會露餡。

## Implementation Decisions

**範圍與定位**
- 獨立新專案，名稱「求職情報問答」，不放進組內專題 repo。
- 目標：11/18 晚上前完成本機可跑版本，11/19 現場演示。超時就砍功能，不加時間。
- 不做：登入、資料庫、ragas 全套、手機版、Hugging Face Spaces（見 Out of Scope）。

**語料與分類**
- 語料：16 家深查檔加 104 全部職缺檔，全部進索引。
- 切塊：依標題切，每塊前面加「公司名＋標題路徑」；太長的段落再細切，大小約 400–512 token，重疊 10–20%，之後依評估結果調整。
- 段落分類為公開事實段落或私人段落，依標題名稱判斷：
  - 公開事實：基本資料、業務財務、部門、職缺、技術堆疊、新聞。
  - 私人：面試、評價、判斷、風險、未查到與限制、你的對應、面談作戰卡。
  - 不在上列的標題一律當私人。實際標題要在建置時對照檔案確認；分類結果要輸出成一張表給我檢查。
- 資料不進 git。公開 repo 含程式、評估題、3 家範例語料。

**檢索**
- 5 種檢索方式：BM25（jieba 斷詞）、bge-small-zh、multilingual-e5、bge-m3、混合（BM25＋bge-m3，以 RRF 合併，k=60，不調權重）。
- 向量索引用 FAISS。語料只有幾百個段落，索引建置時間不是問題。
- 預設檢索方式依評估結果選，由我確認；在評估完成前不預設。
- 公司按鈕以公司為過濾條件，不另建索引。
- 模式過濾在檢索層做：演示模式只回傳公開事實段落，不是回傳後再隱藏。

**查無判斷**
- 檢索一定會回傳結果，所以「查無」需要門檻。用分數門檻判斷，門檻值用評估題的一部分校準，並在研究結果頁寫明。這一項目前沒有定案數值，是待驗證的決定。

**生成**
- 只有「整理成答案」會呼叫 DeepSeek（V4.1 Flash）。實作前先查官方文件確認 API 的實際模型代號，不憑記憶。
- 送給 LLM 的只有公開事實段落。私人段落永不送出，與模式無關。
- 答案必須引用所給段落；沒有可引用的內容時回「查無」。
- 失敗（逾時、無網路、額度或金鑰錯誤）時回明確錯誤，不回示範或假答案。原文結果不受影響。
- 金鑰由使用者填入不進 git 的設定檔。

**介面**
- 單頁應用，兩個分頁：問答、研究結果。
- 問答頁：頂端 11 顆公司按鈕；中間輸入框；其下 6 顆常用問題和 2 顆查無示範；結果區顯示前 3 段；每個結果附「整理成答案」。
- 右上角模式切換；查詢模式用橘色橫幅。
- 按鈕送出的問題文字取自評估題，連到該題成績。
- 預設模式為演示模式。

**評估**
- 30 題：25 題可回答，5 題不可回答。可回答題中包含跨公司題、只問一家的題、問職缺的題、問面試的題；面試與評價相關的題屬於私人段落，只在查詢模式的評估中計算，並與演示模式的成績分開呈現。
- 題目由 AI 草擬，我逐題對照原檔確認金標段落。
- 指標：Hit@1、Hit@3、MRR（可回答題）；正確拒答率（不可回答題，另列）。
- 結果頁寫明 K 值、評分單位（段落）、題數、題目來源與限制。
- 評估只量檢索，不呼叫 LLM。生成品質由我手動檢查 10 題是否忠於出處，結果寫在頁面上。
- 數字由評估程式輸出，結果頁與純文字檔由同一份輸出產生。

**履歷**
- 專案完成、數字產出後才修改履歷。技能欄只有在專案真的使用 FAISS 與 BGE-M3 時才保留 RAG（FAISS、BGE-M3）。
- 履歷數字只抄評估程式的實際輸出。

## Testing Decisions

- **好測試的標準：** 只測外部行為。給定問題、模式、公司，檢查回傳的段落、分類與拒答，不測內部怎麼切塊或怎麼排序。
- **唯一的縫（seam）：** 一個檢索函式，輸入「問題、檢索方式、模式、公司（可選）」，輸出排序後的段落清單，每個段落帶公司、檔名、標題路徑、是否私人、分數。評估程式、介面、查無判斷都只透過它。LLM 呼叫放在它後面，測試時用假的替身。
- **要測的行為：**
  - 演示模式的結果中**不含**任何私人段落（負向測試）。
  - 公司過濾後，結果只含該公司。
  - 沒有被分類的標題一律歸為私人（負向：一個名稱相近但不在清單的標題，例如「風險備註」，必須歸私人）。
  - 不可回答題在門檻下回「查無」。
  - 送給 LLM 的輸入中**不含**私人段落，即使在查詢模式。
  - LLM 失敗時回錯誤，不回示範內容。
  - 標題比對用完全比對，不用子字串（例如「職缺」不應匹配「職缺風險」這類標題）。
  - 評估指標的算法：用一個手算的小例子驗證 Hit@k 與 MRR。
- **前例：** 此資料夾尚無測試。組內專題 repo 有 RAG 測試目錄，可參考其風格；不直接複用其程式。

## Out of Scope

- 手機版與 Hugging Face Spaces。本機完成後再另外決定，且要先確認私人資料放第三方伺服器是否可接受。
- ragas 或其他 LLM 評審的自動評估。
- 登入、多使用者、資料庫、雲端部署。
- 組內專題 RAG 模組的任何修改。
- 履歷與自傳全文的改寫（只在專案完成後改技能欄與專案欄）。
- 比較不同切塊大小。只用一種切法。
- 重排序模型（reranker）。

## Further Notes

- 查無門檻、預設檢索方式、段落分類表是三個要在建置中驗證的決定，不是已知答案。
- 風險：評估題只有 30 題，結果只能當方向，不能當基準。若命中率接近 100%，先懷疑題目太簡單。
- 風險：DeepSeek 的繁體中文摘要品質與延遲沒有測過。現場 Wi-Fi 穩定度未知，所以原文結果是預設，錄影是備案。
- 模型下載來源是 Hugging Face，約 3–4 GB。下載前先查實際大小並回報。
- 使用者要自行準備 DeepSeek 金鑰與餘額。
- 決策紀錄：討論中的決策已整理在本檔；若要寫期末報告，另開決策紀錄檔，且不使用私人編號。
